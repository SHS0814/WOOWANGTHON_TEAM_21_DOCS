### 2. `docs/design/api.md` 신규 (API 계약서)

|---|---|
| "나 약 먹었나?" (E8) | `GET /dose-events/today`의 `elder_status`, `taken_at`, `photos[].url` |
| 보호자 인계 상세 (G5) | `GET /handoffs/{id}`: 사유, 모든 판독(재촬영 포함)과 사진, `layout`, `allowed_verdicts` |

## 헌장과 다르거나 애매한 지점

**R-007 조건 해석**
1. **C2를 "기대 = 차 있음"이 아니라 "비교 제외"로 적었다.** 놓친 약을 나중에 드셔서 칸이 비면, "기대 = 차 있음"에서는 그 칸 때문에 이중 복용 의심으로 다시 인계된다. 그래서 그 칸은 어느 쪽으로도 비교하지 않는다. 대신 그 칸에 정말로 이중 복용이 생겨도 잡지 못한다. 어느 쪽이 맞는지 판단을 바란다
2. **C1의 "모든 칸이 차 있음"을 "대상 칸을 뺀 모든 칸이 full, 그중 기대상 비어 있어야 할 칸이 1개 이상"으로 정의했다.** 대상 칸까지 포함하면, 리필을 기록하지 않은 날 어르신이 정상 복용해도 확인 요청이 안 나간다. 그리고 지난 칸 일부만 기대와 다를 때(예: 하나만 차 있음)는 정의가 없어서 지금은 "애매"(재촬영 → 보호자 판정)로 처리했다. 재촬영해도 결과가 같을 가능성이 높아서 보호자 판정으로 바로 넘기는 편이 나을 수도 있다
3. **리필 확인에 보호자가 "아니요"라고 답한 뒤:** 확인 요청만 닫고, 다음 리필 등록 전까지 같은 확인을 다시 하지 않는 것으로 가정했다. 이 경우 기대 상태가 계속 실제와 어긋난다. "아니요" 뒤에 리필 등록을 안내할지 등 처리 방식을 정해 주길 바란다
4. **이미 무응답으로 인계된 건에 사진이 늦게 왔을 때:** 인계 건에 사진과 판독을 붙이고 `late_photo: true`로 표시한다. 다시 알리지 않고, 정상이어도 인계를 자동으로 닫지 않는다 (판단은 보호자). 어르신 화면은 정상이면 E7a, 아니면 E7c다
5. **리필 안내 기준값 (남은 칸 몇 개 이하):** backend.md에 숫자가 없다. 계약서에는 `threshold_cells` 필드만 두고 모의 데이터는 4로 적었다. 값(또는 "하루 복용 횟수 × N일" 방식)을 정해 주길 바란다
6. **C3와 재촬영 대기 15분이 겹칠 때:** 예를 들어 +28분에 "칸 그대로" 안내(E7d)를 하면 재촬영 기한은 +43분이 된다. 안내 자체는 +30분 안에 했으므로 허용으로 보았다. 기한도 +30분에 맞춰 자를지 판단을 바란다

**보안·운영**
7. **6자리 예비 코드 "5회 틀리면 폐기":** 틀린 입력이 어떤 코드에 대한 것인지 서버가 알 수 없다. 그래서 IP별 10분에 5회 실패로 제한하는 것으로 바꿔 적었다 (backend 3.2, 13장 6번)
8. **사진 위 강조 표시(R-008 C5)는 모델이 칸 위치(`bbox`)를 줄 때만 가능하다.** 지금 판독 프롬프트 초안은 `bbox`를 요구하지 않는다. 계약서에서는 `bbox`를 선택 필드로 두고, 없으면 앱이 격자 그림 위에 강조하는 것으로 정했다. 사진 위 표시를 필수로 할지는 정확도 검증 뒤에 정하자고 제안한다
9. **판독은 동기 방식이다.** 사진 업로드 요청이 판독을 기다렸다가 결과를 돌려준다 (최대 60초, 그동안 E6). 비동기(업로드 후 조회)보다 단순하다. Claude 지연이 길게 나오면 다시 검토한다
10. **시연용 "지금 약 시간" 트리거가 서버에 없다.** 5분 시연 영상에서 복약 시각을 기다릴 수 없다. UI 설계의 "시뮬레이션" 버튼이 실제 서버 흐름을 타려면 데모 가족에서만 쓰는 서버 경로(예: 지금 시각으로 복약 건을 여는 `POST /dev/dose-events`, 화면에 "시뮬레이션" 표시)가 필요하다. 새 기능이라 계약서에 넣지 않았다. 넣을지 판단을 바란다

**API 범위**
11. **★ 추가 경로 7개 (위 2절)** 의 승인을 바란다. 보호자 자신의 표시 이름을 바꾸는 API는 넣지 않았다 (G8 "호칭"은 어르신 호칭으로 해석). 마지막 남은 보호자는 해제할 수 없게 했다 (`409 last_guardian`). backend 3.3의 "어떤 보호자든 다른 보호자를 해제할 수 있다"에 이 제한을 더했다
12. **"나 약 먹었나?"(E8)에서 인계된 건과 `not_taken` 건은 "아직 기록이 없어요"로 보인다** (`elder_status = no_record`). "안 드셨어요"라고 보여주면 늦은 복용을 유도할 수 있어서다 (원칙 6). 보호자가 `taken`으로 판정한 건은 ✓로 보인다
13. **복약 시각 전(`scheduled`) 사진도 받는다.** 알림 전에 미리 드시고 찍는 경우를 위해서다. 이 경우 그 건의 재질문 알림은 취소된다
14. **리필 기준선에서 AI가 `unclear`라고 본 칸은 일단 `full`로 두고 보호자 확인을 요청한다** (`needs_review`). 보호자가 확인하지 않으면 `full`로 남는다. 채운 직후 사진이라 대부분 `full`이라는 가정이다

**AI 판독 (코드)**
15. **판독 프롬프트(`app/reader/prompts.py`)와 Claude·Ollama 판독기는 정확도 검증용 초안이다.** 프로토콜상 판독 방식·프롬프트는 검토 대상이라, 실사진 검증 결과와 함께 따로 검토 요청을 올리겠다. 기본 모델 값은 backend.md 8장 후보에서 `claude-haiku-5-5`, `qwen2.5vl:7b`로 두었고 확정이 아니다
16. **헌장 9장은 "프레임워크·DB 세부는 미정"이지만**, backend.md(R-007 조건부 승인)의 FastAPI·PostgreSQL을 따랐다. 헌장 9장 표 갱신은 사용자 권한이다

- 화면별 데이터 출처 대조표, `attention`으로 신뢰도 숫자를 대신한 방식, `elder_status`로 어르신에게 "안 드셨어요"를 보여주지 않는 설계가 특히 좋다
- 메인 에이전트가 직접 확인한 것: `uv run pytest` 9개 통과, `ruff check` 통과, 커밋 기록에 API 키 없음, `.env.example`에만 빈 키 자리가 있음

API 계약서(`api.md`)와 서버 뼈대를 승인한다. 아래 결정과 조건을 반영해서 엔드포인트 구현(T-BE2)을 시작한다. 서버 뼈대 브랜치는 BE main에 병합한다.

**애매한 지점 16개에 대한 결정**

| # | 결정 |
|---|---|
| 1 | **"비교 제외"로 승인.** 놓친 칸을 나중에 비우는 건 그 끼니의 늦은 복용이지 이중 복용이 아니다. 늦은 복용이 다음 약과 가까운지는 보호자가 판단할 영역이다 |
| 2 | 정의는 승인한다. **지난 칸 일부만 기대와 다를 때는 재촬영하지 않는다.** 대상 칸이 정상이면 복약은 `recorded`(E7a)로 처리한다. 불일치 칸은 판독의 `attention`에 남기고, 하루 요약과 G7에 "약통 상태가 기록과 달라요"로만 보여준다. 어르신에게 재촬영을 시키지 않고, 별도 푸시도 보내지 않는다 (원칙 2·3). 대상 칸이 애매하면 기존대로 애매 처리 |
| 3 | 보호자가 "아니요"라고 답하면 확인 요청을 닫는다. **그때 차 있는 지난 칸들은 C2처럼 비교 제외(`ignored`)로 바꾼다.** 이후 같은 원인으로 다시 묻지 않는다. 앱은 G5에서 "약통을 새로 채우면 리필 등록을 해 주세요" 안내 한 줄만 보여준다 |
| 4 | 승인 (늦은 사진은 붙이기만 하고 재알림 없음, 자동 종결 없음) |
