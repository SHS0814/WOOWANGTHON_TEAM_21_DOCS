선택 이유:

- **추론 강도는 기본값 유지:** 낮추면 빨라지지만, 위험 오류 방향(약이 있는데 빈 칸) 불일치가 나타났다. 근거가 초안 라벨 5장뿐이라 약하지만 원칙 5 쪽으로 정했다. `OPENAI_REASONING_EFFORT`로 코드 수정 없이 바꿀 수 있다
- **지연은 주의:** 기본 강도의 칸 판독은 p50 약 15초, 최대 21초(실서버 복약 사진 4.7~19.6초)다. 앱의 판독 요청 제한 시간은 90초(FE `READING_TIMEOUT_MS`)라 동작은 하지만, R-010 9번(p95 20초 이상이면 비동기 재검토)의 경계에 있다. 어르신 대기가 문제가 되면 `OPENAI_MODEL=gpt-6.1-sol`로 바꾸면 4~5초가 된다(비용 약 8배. 하루 몇 장 기준 월 1달러 미만). 정답 라벨 확인 뒤 정확도와 함께 다시 정하는 것을 제안한다

### 3. 실패 경로 (원칙 5: 서버가 죽거나 정상으로 처리되면 안 됨)

- **OpenAIReader 보강:** 시간 초과는 재시도 없이 바로 실패(대기 시간이 두 배가 되지 않게), 크레딧 없음(`insufficient_quota`, 실제로 겪음)도 재시도 안 함, 5xx·일반 429·연결 오류만 1회 재시도. JSON이 아닌 응답 본문, 이상한 응답 형태, 스키마 밖 값도 모두 `ReaderError` → 서버가 판독 애매로 처리
- **키 없음·판독기 생성 실패:** 전에는 서버 시작 때 `ReaderUnavailable`로 **서버가 뜨지 않았다.** `build_server_reader`가 오류 로그를 남기고 항상 실패하는 판독기를 꽂아, 서버는 뜨고 모든 판독이 애매로 간다 (`app/main.py` 두 줄 변경)
- **테스트** `tests/test_openai_server.py`(11개, 실제 OpenAIReader + 가짜 OpenAI 응답): 등록→복약 전체 흐름, 정상·칸 그대로·애매·낮은 신뢰도, 실패 6종(시간 초과, 거절, 잘못된 JSON, 5xx, 크레딧 없음, HTML 응답)과 키 없음이 모두 **재촬영 → 두 번째에 보호자 인계(unclear)**, 등록 판독 실패는 502 `reading_failed`
- **실서버에서도 확인:** `READER_TIMEOUT_S=1`(실제 시간 초과)과 키 없음으로 서버를 띄워, 서버가 뜨고 `/health` 200, 등록이 502 `reading_failed`로 끝나는 것을 확인

### 4. "정상" 신뢰도 기준 (`backend.md` 13장 1번): **임시로 0.9 유지**를 제안

- 근거(약함, 정답 라벨 없음): luna는 신뢰도를 띄엄띄엄 매긴다. 시험 31칸에서 '빔' 판독 7칸 중 5칸이 0.78~0.83이었고 2칸이 0.95~0.96, '참'은 대부분 0.97~0.99. 실서버에서 정상인 복약 사진 1장이 0.84로 애매 처리됐다
- 0.9를 유지하면 실제로 드신 경우에도 재촬영·인계가 늘어난다(보호자 부담). 0.8로 낮추면 그런 경우 대부분이 기록되지만, '약이 있는데 빈 칸으로 봄' 위험을 정답 라벨 없이 확인할 수 없다. 원칙 5에 따라 **확인 전에는 0.9(현재값) 유지**, 사용자 라벨 확인 뒤 `harness.run --thresholds 0.75,0.8,0.85,0.9`로 위험 오류 0을 지키는 가장 낮은 값을 고르는 것을 제안한다
- 비슷하게, 띠 사진에서 안 보이는 칸이 `unclear`로 오면 분류 규칙상 사진 전체가 애매(재촬영)가 된다. 원칙 5에는 맞지만, 일부만 찍는 습관이 있으면 재촬영이 잦을 수 있다(분류 규칙은 이번 범위 밖, 관찰만)

### 5. FE 문구 확인 (grep만, 수정 없음)

- 동의 화면(`src/app/elder/consent.tsx`): `ai_external_transfer`가 true면 "사진은 약 칸 확인을 위해 AI 서비스로 보내져요." 회사 이름은 없고, openai 판독기에서 이 값이 true가 되는 것을 확인. **고칠 것 없음.** 회사 이름(OpenAI)을 밝힐지는 정책 판단이라 메인 에이전트·사용자 결정으로 남긴다
