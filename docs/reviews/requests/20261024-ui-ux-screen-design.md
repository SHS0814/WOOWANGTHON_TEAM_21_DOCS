# 검토 요청: UI/UX 화면 설계 및 Expo 화면 골격
- 요청자: 작업 에이전트 (worktree `senior-dementia-care-app-ba253440`)
- 날짜: 2026-10-24
- 종류: 설계 (+ 승인 후 코드)
- 관련 헌장 항목: 3장 핵심 컨셉, 4장 MVP #1~7, 5장 원칙 2·3·5·6·7·8, 6장 모킹 표시, 9장 앱 스택

## 무엇을 하려는가

어르신·보호자 화면 구성과 흐름, 문구 원칙을 정하고, 승인되면 바로 Expo(RN + TS)로 화면 골격을 만든다.
백엔드와 AI가 아직 없으므로 화면은 **모의 데이터**로 움직이고, 모의 데이터라는 것을 화면에 표시한다.

### 1. 앱 구조

- 첫 실행 때 역할을 고른다: "어르신 폰으로 쓰기" / "보호자 폰으로 쓰기"
- 어르신 모드는 보호자 화면으로 가는 길을 두지 않는다 (실수로 들어가는 것 방지). 역할 변경은 보호자 폰에서 연결을 해제할 때만 가능하다
- 페어링은 R-004를 따른다: 어르신 폰이 QR을 띄우고 보호자 폰이 스캔한다

### 2. 어르신 화면 (원칙 3: 화면 하나에 행동 하나)

| # | 화면 | 내용 | 행동 |
|---|---|---|---|
| E1 | 동의 | "민수가 어머니 약 드시는 걸 같이 챙기려고 해요. 약통 사진을 민수만 볼 수 있어요." | [좋아요] 하나 (원칙 8) |
| E2 | 연결 QR | QR과 "민수 폰으로 이걸 찍어주세요" | 없음 (완료되면 자동으로 넘어감) |
| E3 | 대기 홈 | 오늘 날짜·요일을 크게. 다음 약 시간 | **[나 약 먹었나?]** 하나 |
| E4 | 복약 시간 질문 | "어머니, 저녁 약 드실 시간이에요. 드시고 약통 사진 한 장 찍어주실래요?" | [사진 찍기] 하나 |
| E5 | 촬영 | 약통을 맞출 가이드 틀과 "약통이 다 보이게 찍어주세요" | 셔터 하나 (아주 크게) |
| E6 | 판독 중 | "확인하고 있어요" | 없음 |
| E7a | 결과: 정상 | "고마워요. 저녁 약 기록해 뒀어요." 몇 초 뒤 E3로 | 없음 |
| E7b | 결과: 애매 | "사진이 잘 안 보여요. 한 번만 더 찍어주실래요?" | [다시 찍기] (재촬영 1회 뒤에도 애매하면 보호자 판정으로 넘김) |
| E7c | 결과: 칸이 그대로 / 이중 의심 | "알겠어요. 민수한테 알려둘게요." | 없음. **추가 복용 지시는 하지 않는다** (원칙 6) |
| E8 | 나 약 먹었나? | 오늘 시간대별로 "아침 ✓ 8시 12분" + 그때 사진. 아직이면 "아직 기록이 없어요" | [돌아가기] |

- 글씨: 본문 최소 28pt, 버튼 높이 최소 72pt에 가로 전체. 대비가 높은 색을 쓰고, 색만으로 상태를 구분하지 않는다 (✓ 같은 기호와 글자를 함께 쓴다)
- 말투: 가족이 묻는 존댓말. "확인하세요", "미복용" 같은 감시·의료 용어는 쓰지 않는다
- 호칭("어머니", "민수")은 페어링할 때 보호자가 입력한다. 하드코딩하지 않는다
- E8 하단에 작게 "사진으로 약 칸이 빈 것만 확인해요" (원칙 7)
- 제안(선택): E4·E7 문구를 소리로 읽어주기 (expo-speech). MVP #1 안의 보조 수단이고 새 기능은 아님. 판단을 받고 싶음

### 3. 보호자 화면

| # | 화면 | 내용 |
|---|---|---|
| G1 | 연결 | QR 스캔, 호칭 입력 ("어머니" / "민수") |
| G2 | 약통 등록 | 빈 약통이나 채운 약통 사진 → AI가 칸 구조 제안 (예: 7×2, 요일 × 아침/저녁) → 보호자가 격자에서 요일·시간대 매핑을 확인하거나 고침 (원칙 4) |
| G3 | 복약 시각 | 시간대별 시각 (아침 8:00, 저녁 19:00 등) |
| G4 | 홈 | 맨 위 "처리할 일" (인계 건이 있을 때만 나옴), 그 아래 오늘 상태 한 줄 ("오늘 2번 모두 정상"). 정상인 날은 거의 비어 있는 화면이 정상이다 (원칙 2) |
| G5 | 인계 상세 | 사유 (무응답 / 판독 애매 / 칸 그대로 / 이중 의심), 사진, AI가 본 칸 표시와 신뢰도, [전화하기]. 판독 애매 건은 **[드심] / [안 드심]** 판정 (MVP #5) |
| G6 | 기록 | 하루·주간 요약 (MVP #6). 정상 주간은 "이번 주 14번 중 14번 정상" 한 줄 |
| G7 | 리필 | 남은 칸 수와 "목요일 저녁까지 남았어요" (MVP #7). 알림은 남은 칸이 기준 이하일 때 하루 1번 |
| G8 | 설정 | 호칭, 시각, 약통 재등록, 연결 해제 |

- 모든 판독 결과 옆에 "AI 판독" 표시. 보호자가 판정한 건은 "민수 판정"으로 구분한다 (원칙 1)
- G5에 한계 문구: "칸이 빈 것만 확인했어요. 드셨는지는 직접 확인해 주세요" (원칙 7)

### 4. 알림 (어르신 폰) — OS 전략

사용자 결정: Android와 iOS 둘 다 고려한다.

| | Android (기준) | iOS (축소 동작) |
|---|---|---|
| 복약 시간 | 잠금 화면 위 전체 화면 E4 + 알람음 (full-screen intent) | 시간 민감(time-sensitive) 알림. 탭하면 E4가 열림 |
| 재요청 | 같은 방식으로 반복 | 로컬 알림을 반복 예약 |

- 기술 리스크: full-screen intent는 Expo Go에서 안 되고 개발 빌드(EAS)와 네이티브 모듈(notifee 등)이 필요하다. Android 14부터 이 권한이 알람·통화 앱 외에는 기본 거부라서 설정에서 허용하도록 안내하는 화면이 하나 필요하다
- 화면 골격 단계에서는 "지금 약 시간 시뮬레이션" 버튼으로 E4를 띄운다 (시연 시 **"시뮬레이션"** 표시)

### 5. 모킹 표시 (6장)

- 백엔드·AI 연결 전에는 판독 결과를 모의 데이터로 만든다. 이때 화면 상단에 **"모의 판독 (실제 AI 아님)"** 띠를 항상 띄운다
- 개발용 모드 전환 스위치로 정상/애매/칸 그대로/이중 의심을 고를 수 있게 해서 전 화면을 확인한다. 실제 AI가 붙으면 띠를 없앤다

## 왜 필요한가

- 7장: 어르신 폰 → AI → 보호자 폰 흐름을 끝까지 보여주는 것이 구현 완성도(25)의 핵심이다. 화면이 먼저 있어야 백엔드·AI를 붙여 가며 흐름을 검증할 수 있다
- 8장 일정의 "~11/1 앱 뼈대"에 해당한다
- 원칙 2·3·6·7이 문구와 화면에서 지켜지는지 미리 합의해야 나중에 다시 만들지 않는다

## 범위와 예상 소요 시간

- 승인 후 Expo 프로젝트 생성, 라우팅(expo-router), 역할 분기, E1~E8, G1~G8 화면을 모의 데이터로 구현: **약 2~3일 (~10/27)**
- 포함하지 않음: 서버 통신, 실제 AI 판독, 실제 푸시·full-screen intent (별도 요청), 연락두절 감지(선택 #8)

## 헌장과 다르거나 애매한 지점

1. **E4 문구 "드시고 사진 찍어주세요"**: 정해진 시간에 정해진 약을 드시라고 알려주는 것은 지금 보호자가 하는 일(3장)이라 의료 조언이 아니라고 봤다. 반대로 E7c(칸이 그대로)에서는 "지금 드세요"라고 하지 않고 보호자에게만 넘긴다. 이 경계가 원칙 6에 맞는지 판단을 바란다
2. **재요청 간격과 횟수**: 헌장은 "2~3회"까지만 정했다. 화면 골격에서는 10분 간격 3회 뒤 보호자 인계(+30분)로 가정한다. 인계 규칙은 별도 검토 대상이라 여기서는 가정값으로만 쓴다
3. **판독 애매 시 재촬영 횟수**: 1회 재촬영 뒤에도 애매하면 보호자 판정으로 넘긴다고 가정했다
4. **음성 읽어주기**: 범위 안의 보조 수단으로 보는지 판단을 바란다
5. **iOS 축소 동작**: iOS에서는 MVP #1의 "전체 화면으로 질문"이 완전히 되지 않는다. 발표에서 이 차이를 명시하는 것으로 충분한지 판단을 바란다

## 메인 에이전트 판정: 🟡 조건부 승인 (R-008, 2026-10-24)

**전체 평가:** 원칙 2·3·6·7을 화면과 문구 수준에서 구체화했다. 다음이 특히 좋다.
- 정상인 날은 거의 비어 있는 보호자 홈
- 색만으로 상태를 구분하지 않는 것
- E7c에서 복용을 지시하지 않는 것
- 모의 판독 띠와 시뮬레이션 표시

다만 같은 날 올라온 백엔드 설계(R-007), 사용자 결정 R-006과 어긋나는 곳이 있다. 아래 조건을 반영한 뒤 화면 골격 작성을 시작한다.

**질문에 대한 답**
1. E4 "드시고 사진 찍어주세요" → 승인. 정해진 시각에 알리는 것은 지금 보호자가 하는 일이라 의료 조언이 아니다. E7c 경계도 맞다
2. 재요청 간격·횟수 → **R-006을 따른다.** 2회(+10/+20분), +30분에 인계. 화면 골격의 가정값도 이 값으로 바꾼다 (조건 2)
3. 애매할 때 재촬영 1회 뒤 보호자 판정 → 승인. 백엔드와 일치한다
4. 음성 읽어주기 → 범위 안의 보조 수단으로 승인. **단, 화면 골격과 MVP 1~5가 끝난 뒤** 작업한다
5. iOS 축소 동작 → 승인. 시연과 배포는 Android(APK)를 기준으로 하고, iOS 차이는 발표의 "한계"에 명시한다

**조건 (반영 필수)**
- **C1. 짝짓기 방향을 백엔드(R-007, `docs/design/backend.md` 3.2)에 맞춘다.** 보호자가 먼저 가족을 만들고 코드를 발급한다. 보호자가 어르신 폰으로 그 QR을 스캔한다. 인증된 보호자만 코드를 발급하는 쪽이 안전하기 때문이다. 이에 따라 E2와 G1을 바꾼다
  - 순서: G1(가족 만들기와 호칭 입력) → 보호자 폰에 QR 표시 → 어르신 폰에서 스캔 → E1 동의 → 완료
  - 동의(E1)는 짝짓기 **이후**에 한다. 그래야 실제 보호자 이름을 보여줄 수 있다
- **C2. 칸이 그대로일 때의 화면을 R-006에 맞춘다.** 지금 E7c는 바로 인계한다. 다음과 같이 나눈다
  - 새 화면 E7d (칸 그대로, 첫 번째, 복약 시간 안): "약 드실 시간이에요. 드시고 한 번만 더 찍어주실래요?" [사진 찍기]
  - E7c (두 번째로도 그대로, 이중 복용 의심, 복약 시간 지남): "○○님께 알려드렸어요." 지시 문구는 넣지 않는다
- **C3. 약통 등록(G2)은 "채운 약통" 사진으로 통일한다.** 이 사진이 기준선이 된다. 리필 화면(G7)에 **[약통 채웠어요 + 사진 찍기]** 동작을 넣는다 (R-007 조건 C1)
- **C4. 외부 AI 전송 사실을 동의 화면(E1)에 반영한다.** Claude API를 쓰기로 결정되면 E1에 큰 글씨로 한 줄 넣는다. 예: "사진은 약 칸 확인을 위해 AI 서비스로 보내져요"
- **C5. 모델이 매긴 원본 신뢰도 숫자를 보호자에게 그대로 보여주지 않는다 (G5).** 보정되지 않은 수치라 오해를 부를 수 있다. 대신 "AI가 확실하지 않다고 본 칸"을 사진 위에 강조 표시한다
