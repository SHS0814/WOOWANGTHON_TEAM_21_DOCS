- 작성일: 2026-10-24
- 상태: **비교는 미룸 (R-037).** 우선 GPT로 실제 판독을 작동시키는 T-AI2를 한다. 1단계 준비물(부분 사진 라벨, 확인 시트, OpenAIReader)은 완료(R-036)
- 관련: 헌장 5장 원칙 4·5, 8장 일정 (~11/1 정확도 검증), 9장 AI 판독 모델, `backend.md` 8장·13장, R-010 결정 8·15번

1. 매일 판독(`read_cells`)과 약통 등록(`detect_layout`)에 쓸 모델을 숫자로 정한다
2. "정상" 판정 신뢰도 기준을 정한다 (`backend.md` 13장 1번)
3. 사진 위 강조 표시(`bbox`)를 필수로 할지 정한다 (R-010 결정 8번)
4. 발표의 "실제 결과·오류와 한계"와 AI 활용도 근거 자료를 만든다

## 진행 방식

- **위치:** BE 저장소 `WOOWANGTHON_TEAM_00_BE`, 브랜치 `ai/model-eval` (BE main에서 분기). 판독기 추가와 하네스 개선만 하고, 서버 엔드포인트는 건드리지 않는다
- **도구:** 이미 있는 정확도 검증 하네스 (`harness/`)를 쓴다. 모든 모델이 **같은 사진, 같은 라벨, 같은 프롬프트**로 돌아야 한다. 모델별로 프롬프트를 바꿔야 하면 그 사실을 결과에 적는다
- **데이터:** 사용자가 `harness/data/`에 실사진과 라벨을 넣는다 (`.gitignore` 대상, 커밋하지 않음)
  - 목표 30~50장. 할머니 약통을 포함한 여러 종류의 약통 (1×7, 2×7, 3×7, 4×7, 세로 배열 등)
  - 상태를 섞는다: 모두 참, 모두 빔, 일부만 빔, 다른 날 칸이 빈 경우 (이중 복용 상황)
  - 조건을 섞는다: 밝기, 각도, 흔들림, 뚜껑 반사, 손가락 가림
- **API 키:** 사용자가 BE 저장소의 `.env`에 직접 넣는다. 대화나 커밋에 넣지 않는다. 비용 상한을 각 콘솔에서 설정한다

## 실사진 데이터 (2026-10-25 도착)

사용자가 DOCS 저장소 `data/`에 넣었다 (`.gitignore` 대상). 할머니가 실제로 보호자에게 보냈던 사진이다. 할머니는 **사진을 찍고, 화면을 캡처하고, 잘라서** 보냈다.

- 54개 파일, 같은 파일 4쌍을 빼면 **50장**
- 약통은 1종: **1×7 요일 약통**(月火水木金土日 한자 표기, 투명 뚜껑)
- 약은 알약이 아니라 **처방 약봉투**가 칸에 접혀 들어 있다. "참"은 봉투가 있는 것, "빔"은 봉투가 없는 것
- **41장은 약통 부분만 가로로 길게 자른 띠**(약 1400×300)이고, 9장은 약통 전체가 보이는 원본 사진(1050×1400 또는 1400×1050, 세로·가로 배치 모두 있음). 띠 사진도 대부분 7칸이 다 보인다. 일부 칸만 보이는 사진은 몇 장이고, 안 보이는 칸은 사용자 확인 뒤 350칸 중 6칸이다 (초안은 9칸. 처음에 "대부분 일부 칸만 보인다"고 적은 것은 메인 에이전트의 잘못된 판단이라 고침)
- 찍은 날짜를 알 수 없다 (파일 시각은 카카오톡에서 내보낸 시각). 그래서 "이번 칸"은 사진에서 추정한다

계획과 다른 점과 대응:

1. **약통 종류가 하나뿐이다.** 범용성(헌장)은 이 데이터로 증명할 수 없다. 결과에 "1종으로만 검증"이라고 적고, 다른 약통 사진은 합성 샘플과 추가 촬영으로 보완한다
2. **잘린 사진은 앱 실사용과 다르다.** 앱은 카메라로 바로 찍는다. 그래도 "어르신이 약통 일부만 찍는" 경우가 실제로 있으므로, 일부 칸만 보이는 사진을 처리하는 방법(요일 글자로 칸 위치를 맞추기, 안 보이는 칸은 애매로)을 함께 검증한다
3. **약봉투는 알약보다 판독이 쉽거나 어려울 수 있다** (흰 봉투와 투명 뚜껑의 반사). 프롬프트는 약통 내용물 종류를 가리지 않게 쓴다
4. **정답 라벨을 판독 후보 모델로 만들면 안 된다.** AI 에이전트가 라벨 초안을 만들 수는 있지만, **사용자가 한 장씩 확인한 라벨만 정답으로 쓴다**. 확인 전 라벨로 낸 숫자는 결과에 쓰지 않는다
5. **개인정보:** 약봉투에 약국·이름이 찍혀 있을 수 있다. 사진과 판독 결과는 커밋하지 않는다. 발표 자료에 쓰는 사진은 사용자가 고르고 글자를 가린다. 외부 API로 보내는 것은 사용자가 이 데이터를 넣고 검증을 지시한 것으로 동의한 것으로 본다

## 진행 상황 (2026-10-25)

- 사용자 결정: **OpenAI 키만 먼저 넣었다. Anthropic은 크레딧이 없어 Claude 그룹은 보류**한다. 크레딧이 생기면 같은 조건으로 추가한다. 그 전까지 비교는 GPT와 로컬 모델로 한다
- 정답 라벨은 사용자 확인 대기. 확인 전에는 연결·지연·비용 확인용 시험 실행(소수 사진, `--allow-draft`)만 하고 정확도 숫자는 쓰지 않는다


- 칸 정확도, 판단한 칸 정확도, 애매 비율
- **약이 있는데 빈 칸으로 본 오류** (가장 위험. 복용하지 않았는데 "드심"으로 기록될 수 있음)
- 빈 칸인데 약이 있다고 본 오류
- 대상 칸 정확도, 사진 전체 정답률, 구조 인식 정확도
- 지연 p50/p95 (R-010 결정 9번: p95가 20초 이상이면 비동기 판독을 다시 검토)
- 사진 1장당 비용 (API 모델)

## 선택 기준 (초안, 결과를 보고 사용자와 확정)

1. 위험 오류(약이 있는데 빈 칸으로 봄)가 가장 적은 모델을 우선한다. 원칙 5에 따라, 확실하지 않으면 애매로 돌리는 모델이 낫다
2. 정확도가 비슷하면 비용과 지연이 낮은 쪽, 그다음 로컬 모델을 우선한다 (개인정보, 원칙 8)
3. 등록(`detect_layout`)과 매일 판독(`read_cells`)에 서로 다른 모델을 쓸 수 있다
