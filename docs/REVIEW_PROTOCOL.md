# 검토·승인 절차 (Review Protocol)

## 역할

| 역할 | 누가 | 권한 |
|---|---|---|
| 프로젝트 오너 | 사용자 | 최종 결정권. 헌장 변경, 거절 건 재검토, 승인 번복 |
| 메인 에이전트 | 지정된 Claude 세션 (리뷰어) | 계획·설계·코드를 헌장에 비추어 검토하고 승인 또는 거절 |
| 작업 에이전트 | 그 외 모든 Claude 세션 | 계획 수립, 코드 작성. **중요한 작업은 메인 에이전트의 승인을 받은 뒤 진행·병합** |

## 검토가 필요한 작업

- 기능 추가, 기능 범위 변경
- 기술 스택, 아키텍처, 데이터 모델 결정
- AI 판독 방식, 프롬프트, 인계 규칙(언제 보호자에게 알릴지) 결정
- 어르신·보호자 화면 설계
- main 브랜치 병합 전 코드 변경
- 시연 영상, 발표 자료 구성

오타 수정이나 포맷팅 같은 사소한 변경은 검토 없이 진행해도 된다.

## 검토 요청 방법 (작업 에이전트)

`docs/reviews/requests/` 에 파일을 하나 만든다. 파일명은 `YYYYMMDD-짧은-제목.md` 형식이다.

```markdown
# 검토 요청: <제목>
- 요청자: <세션/에이전트 이름>
- 날짜: YYYY-MM-DD
- 종류: 기능 / 설계 / 코드 / 기술스택 / 발표 / 기타
- 관련 헌장 항목: 예) 4장 MVP #2, 5장 원칙 4

## 무엇을 하려는가

## 왜 필요한가 (어떤 MVP 항목, 어떤 심사 항목에 기여하는가)

## 범위와 예상 소요 시간

## 관련 파일·브랜치·커밋

## 헌장과 다르거나 애매한 지점 (있으면 반드시 적기)
```

그 다음 **메인 에이전트에게 직접 알린다** (아래 "완료·검토 요청 알림").

## 완료·검토 요청 알림 (작업 에이전트 → 메인 에이전트)

작업을 끝냈거나(SUPERSET_WORKER_DONE), 막혔거나(SUPERSET_WORKER_BLOCKED), 검토 요청을 올렸으면 사용자를 거치지 않고 메인 에이전트 터미널에 직접 알린다. 명령은 두 개다 (텍스트 입력 후 Enter).

```bash
superset terminals send --workspace ba253440-b4bd-4f55-bcc2-25ef1392fca5 \
  --terminal 3a4f8cab-c8aa-429d-b4bf-e8a557118442 \
  --text "[작업 알림] <작업 ID> <DONE|BLOCKED|REVIEW>: <한 줄 요약>. 보고 위치: <요청 파일 경로 또는 '내 터미널'>. 워크스페이스 <내 workspace id>, 터미널 <내 terminal id>" --json
superset terminals send --workspace ba253440-b4bd-4f55-bcc2-25ef1392fca5 \
  --terminal 3a4f8cab-c8aa-429d-b4bf-e8a557118442 --keys enter --json
```

- 메시지는 한 줄로 짧게 쓴다. 자세한 내용은 요청 파일이나 자기 터미널의 완료 보고에 남긴다
- 자기 workspace id는 `$SUPERSET_WORKSPACE_ID`에 있다. 터미널 id를 모르면 `superset terminals list --workspace $SUPERSET_WORKSPACE_ID --json`으로 찾는다
- 알림을 보낸 뒤에는 메인 에이전트의 판정이 터미널로 올 때까지 기다린다. 판정을 기다리지 않아도 되는 독립 작업이 있으면 진행해도 된다
- 메인 에이전트 세션이 바뀌면 이 터미널 id도 바뀐다. 메인 에이전트가 이 문서를 갱신한다


## 판정 기준 (메인 에이전트)

검토할 때 다음을 순서대로 확인한다.
1. **대회 제약 위반** (헌장 6장): 하나라도 위반하면 거절
2. **핵심 컨셉 이탈** (헌장 3장): 앱이 보호자 역할을 대신하고 예외만 넘기는 구조를 벗어나면 거절
3. **범위**: 범위 밖 기능이면 거절. MVP가 끝나기 전에 선택 기능을 하면 보류
4. **설계 원칙** (헌장 5장): 위반하면 거절하거나 조건부 승인
5. **일정**: 1인 개발로 마감 안에 끝낼 수 있는가
6. **심사 기여도**: 구현 완성도와 핵심 흐름에 기여하는가

## 판정 종류

| 판정 | 의미 | 다음 단계 |
|---|---|---|
| ✅ 승인 | 그대로 진행 | 작업 에이전트가 진행 |
| 🟡 조건부 승인 | 명시한 조건을 반영하면 진행 | 조건을 반영한 뒤 진행 |
| ⏸ 보류 | 방향은 맞지만 지금 할 일이 아님 | 순서가 오면 다시 요청 |
| ❌ 거절 | 헌장과 맞지 않음 | **사용자가 재검토할 때까지 진행 금지** |

## 기록

- 모든 판정은 `docs/REVIEW_LOG.md` 에 기록한다
- **거절과 보류 건은 사용자가 확인할 수 있도록 "사용자 검토 대기" 표에 올린다**
- 사용자가 결정하면 해당 행에 결정 내용과 날짜를 적는다. 사용자가 승인하면 그 결정이 메인 에이전트 판정보다 우선한다
- 사용자의 결정으로 헌장이 바뀌면 `docs/PROJECT_CHARTER.md` 를 갱신하고, 변경 이력을 로그에 남긴다
