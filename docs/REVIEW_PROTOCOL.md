# 검토·승인 절차 (Review Protocol)

## 역할

| 역할 | 누가 | 권한 |
|---|---|---|
| 프로젝트 오너 | 사용자 | 최종 결정권. 헌장 변경, 거절 건 재검토, 승인 번복 |
| 메인 에이전트 | 지정된 Claude 세션 (리뷰어) | 계획·설계·코드를 헌장에 비추어 검토하고 승인 또는 거절 |
| 작업 에이전트 | 그 외 모든 Claude 세션 | 계획 수립, 코드 작성. **중요한 작업은 메인 에이전트의 승인을 받은 뒤 진행·병합** |

## 검토가 필요한 작업

- 기능 추가, 기능 범위 변경
- 기술 스택, 아키텍처, 데이터 모델 결정
- AI 판독 방식, 프롬프트, 인계 규칙(언제 보호자에게 알릴지) 결정
- 어르신·보호자 화면 설계
- main 브랜치 병합 전 코드 변경
- 시연 영상, 발표 자료 구성

오타 수정이나 포맷팅 같은 사소한 변경은 검토 없이 진행해도 된다.

## 검토 요청 방법 (작업 에이전트)

`docs/reviews/requests/` 에 파일을 하나 만든다. 파일명은 `YYYYMMDD-짧은-제목.md` 형식이다.

```markdown
# 검토 요청: <제목>
- 요청자: <세션/에이전트 이름>
- 날짜: YYYY-MM-DD
- 종류: 기능 / 설계 / 코드 / 기술스택 / 발표 / 기타
- 관련 헌장 항목: 예) 4장 MVP #2, 5장 원칙 4

## 무엇을 하려는가

## 왜 필요한가 (어떤 MVP 항목, 어떤 심사 항목에 기여하는가)

## 범위와 예상 소요 시간

## 관련 파일·브랜치·커밋

## 헌장과 다르거나 애매한 지점 (있으면 반드시 적기)
```

그 다음 **메인 에이전트에게 직접 알린다** (아래 "완료·검토 요청 알림").

## 완료·검토 요청 알림 (작업 에이전트 → 메인 에이전트)

작업을 끝냈거나(SUPERSET_WORKER_DONE), 막혔거나(SUPERSET_WORKER_BLOCKED), 검토 요청을 올렸으면 사용자를 거치지 않고 메인 에이전트 터미널에 직접 알린다. 명령은 두 개다 (텍스트 입력 후 Enter).

```bash
superset terminals send --workspace ba253440-b4bd-4f55-bcc2-25ef1392fca5 \
  --terminal c9ed147d-6611-4117-a302-50c594b4ca00 \
  --text "[작업 알림] <작업 ID> <DONE|BLOCKED|REVIEW>: <한 줄 요약>. 보고 위치: <요청 파일 경로 또는 '내 터미널'>. 워크스페이스 <내 workspace id>, 터미널 <내 terminal id>" --json
superset terminals send --workspace ba253440-b4bd-4f55-bcc2-25ef1392fca5 \
  --terminal c9ed147d-6611-4117-a302-50c594b4ca00 --keys enter --json
```

- 메시지는 한 줄로 짧게 쓴다. 자세한 내용은 요청 파일이나 자기 터미널의 완료 보고에 남긴다
- 자기 workspace id는 `$SUPERSET_WORKSPACE_ID`에 있다. 터미널 id를 모르면 `superset terminals list --workspace $SUPERSET_WORKSPACE_ID --json`으로 찾는다
- 알림을 보낸 뒤에는 메인 에이전트의 판정이 터미널로 올 때까지 기다린다. 판정을 기다리지 않아도 되는 독립 작업이 있으면 진행해도 된다
- 메인 에이전트 세션이 바뀌면 이 터미널 id도 바뀐다. 메인 에이전트가 이 문서를 갱신한다


## 판정 기준 (메인 에이전트)

검토할 때 다음을 순서대로 확인한다.
1. **대회 제약 위반** (헌장 6장): 하나라도 위반하면 거절
2. **핵심 컨셉 이탈** (헌장 3장): 앱이 보호자 역할을 대신하고 예외만 넘기는 구조를 벗어나면 거절
3. **범위**: 범위 밖 기능이면 거절. MVP가 끝나기 전에 선택 기능을 하면 보류
4. **설계 원칙** (헌장 5장): 위반하면 거절하거나 조건부 승인
5. **일정**: 1인 개발로 마감 안에 끝낼 수 있는가
6. **심사 기여도**: 구현 완성도와 핵심 흐름에 기여하는가

## 판정 종류

| 판정 | 의미 | 다음 단계 |
|---|---|---|
| ✅ 승인 | 그대로 진행 | 작업 에이전트가 진행 |
| 🟡 조건부 승인 | 명시한 조건을 반영하면 진행 | 조건을 반영한 뒤 진행 |
| ⏸ 보류 | 방향은 맞지만 지금 할 일이 아님 | 순서가 오면 다시 요청 |
| ❌ 거절 | 헌장과 맞지 않음 | **사용자가 재검토할 때까지 진행 금지** |

## 기록

- 모든 판정은 `docs/REVIEW_LOG.md` 에 기록한다
- **거절과 보류 건은 사용자가 확인할 수 있도록 "사용자 검토 대기" 표에 올린다**
- 사용자가 결정하면 해당 행에 결정 내용과 날짜를 적는다. 사용자가 승인하면 그 결정이 메인 에이전트 판정보다 우선한다
- 사용자의 결정으로 헌장이 바뀌면 `docs/PROJECT_CHARTER.md` 를 갱신하고, 변경 이력을 로그에 남긴다

## 에이전트 구조와 운영 (R-017, 2026-10-24 사용자 결정)

### 구성
| 구성원 | 일하는 곳 | 역할 | 하지 않는 것 |
|---|---|---|---|
| 사용자 | — | 최종 결정 (헌장, 기술·모델, 거절 건 재검토). 질문함 확인 시점 지시 | — |
| 메인 에이전트 | DOCS 워크스페이스 | 작업 지시, 검토·판정(직접 테스트 실행), main 병합, `REVIEW_LOG.md` 기록. Notion에는 판정 행·커밋 기록 행·업무 생성과 상태를 쓴다. 사용자가 요청하면 질문함을 확인해서 대상 에이전트에게 넘긴다 | 헌장 변경, 사용자 결정 번복 |
| BE 에이전트 | BE 저장소 | 서버 구현. API를 바꾸면 Notion API 엔드포인트 DB를 갱신한다 | 승인 없이 설계·계약서 변경, main 병합 |
| FE 에이전트 | FE 저장소 | 앱 구현 | 승인 없이 설계 변경, main 병합 |
| AI 에이전트 | BE 저장소 `ai/model-eval` 브랜치 | 판독 모델 비교 검증 (실사진 데이터가 오면 시작) | 서버 엔드포인트 수정 |
| QA 에이전트 | FE+BE를 함께 띄워 테스트 | 시나리오 테스트, 원칙 위반 점검(의료 지시 문구, 모의 표시 누락, 정상인데 보호자 알림 등), 계약서 불일치 탐지. Notion 이슈 DB에 버그를 올린다. 테스트 코드 작성은 허용 | 제품 코드 수정 (수정은 BE·FE 에이전트) |
| Notion 세션 | Notion | Notion DB·페이지 구조 담당 | 판정·업무 상태 동기화 |
| Notion Agent (Notion 내장 AI) | Notion | Claude 에이전트가 적은 원재료를 최종 정리 (API 안내 페이지, 개발 타임라인, 주간 요약). 모르는 것은 질문함에 올린다 | 결과를 바로 확정 (사람이 검토) |

- 이름: 에이전트는 역할 이름(BE 에이전트, FE 에이전트, AI 에이전트, QA 에이전트)으로 부른다. `T-BE2` 같은 번호는 **작업**에만 쓴다
- 지금까지 쓴 이전 세션(기술 스택 결정, UI/UX 설계)은 종료했다

### 기록 위치
| 무엇 | 원본 | Notion에 적는 사람 | Notion Agent가 정리하는 것 |
|---|---|---|---|
| 헌장·설계·검토 기록 | 레포 `docs/` | 메인 에이전트 (판정 행) | — |
| 업무 상태 | — | 작업 에이전트 (자기 업무 행의 상태·진행 메모·브랜치·커밋만), 메인 에이전트 (업무 생성·완료 처리) | — |
| API | 레포 `docs/design/api.md` | BE 에이전트 (API 엔드포인트 DB) | 화면·기능별 API 안내 페이지 |
| 커밋 | 각 저장소 git | 메인 에이전트 (main 병합 때 `git log`로 커밋 기록 DB 채움) | 작업별·날짜별 개발 타임라인, 주간 개발 요약 |
| 버그 | — | QA 에이전트 (이슈 DB) | QA 현황 요약 |
| 질문 | — | Notion Agent (질문함) → 답변: 대상 Claude 에이전트 | — |

- 레포가 원본이다. Notion과 다르면 레포 기준으로 Notion을 고친다
- 작업 에이전트는 검토 DB·회의·결정 DB에 행을 만들지 않는다. 판정 행은 메인 에이전트가 만든다 (중복 방지)

### 질문함 운영
- Notion Agent가 질문함 DB에 질문을 올린다 (대상, 근거 필요 여부 표시)
- **사용자가 "질문 확인해"라고 하면** 메인 에이전트가 열린 질문을 읽고, 직접 답하거나 대상 에이전트에게 넘긴다. 자동으로 주기 확인하지 않는다
- 답변에는 근거(레포 경로, 커밋, 판정 ID)를 붙이고 상태를 "답변됨"으로 바꾼다

### 하루 마무리
- **작업이 있었던 날만** 각 에이전트가 회의·결정 기록에 `에이전트 보고` 1건(한 일, 막힌 것, 다음 할 일)을 남긴다. 작업 에이전트의 보고는 메인 에이전트가 모아서 쓴다
